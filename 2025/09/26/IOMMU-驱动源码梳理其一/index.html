IOMMU 驱动源码梳理其一

Linux kernel 5.15，drivers/iommu/*

宏观组织

1. Core & 通用辅助

  • iommu.c：核心子系统：管理 iommu_domain / iommu_group，核心 API（map/unmap/attach/detach）、bus 注册，初始化都在这里。
  • iova.c：IOVA 分配器（bitmap / rb-tree 分配，保证 IOVA 空间管理）。
  • dma-iommu.c：DMA-API glue，把 dma_map_* 调用转化成 IOMMU 操作（实现 struct dma_map_ops 的 iommu 版本）。
  • iommu-sysfs.c：在 sysfs 下导出 IOMMU group/domain 信息。
  • iommu-debugfs.c：提供 debugfs 接口。
  • iommu-traces.c：定义 tracepoints，用于调试和性能分析。
  • ioasid.c：管理 IO Address Space ID（PASID 等），在 SVA（共享虚拟地址）场景下使用。
  • iommu-sva-lib.c/h：SVA（Shared Virtual Addressing）辅助库，核心代码用于进程地址空间和 IOMMU 绑定。
  • io-pgfault.c：SVA 相关的 page fault 处理（IOMMU faults）。

2. Page Table Framework

  • io-pgtable.c：抽象 IOMMU 页表操作框架（generic io-pgtable API）。
  • io-pgtable-arm.c / io-pgtable-arm-v7s.c：ARM 硬件页表格式的具体实现。
  • omap-iopgtable.h：OMAP IOMMU 的特殊页表定义。

3. IRQ Remapping

  • irq_remapping.c / irq_remapping.h：x86 IOMMU（Intel/AMD）中断重映射支持。

4. 厂商/SoC 特定驱动

  • Intel (drivers/iommu/intel/)
    • iommu.c：Intel VT-d 核心驱动，probe + ops 实现。
    • dmar.c：解析 ACPI DMAR 表。
    • irq_remapping.c：VT-d 中断重映射实现。
    • pasid.c：PASID 支持。
    • svm.c：共享虚拟内存 (SVM)。
    • perf.c：性能监控支持。
    • 其他 debugfs.c、trace.c、cap_audit.c 属于辅助工具。
  • AMD (drivers/iommu/amd/)
    • init.c / iommu.c：AMD-Vi 核心驱动与初始化。
    • iommu_v2.c：IOMMU v2 支持（GPU SVM 相关）。
    • io_pgtable.c：AMD 特有页表。
    • debugfs.c / quirks.c：调试与硬件 workaround。
  • ARM (drivers/iommu/arm/)
    • arm-smmu/arm-smmu.c：SMMU v2/v1 驱动。
    • arm-smmu-v3/arm-smmu-v3.c：SMMU v3 驱动。
    • 里面的 *-impl.c, *-qcom.c, *-nvidia.c 是厂商/SoC 特定实现。
    • arm-smmu-v3-sva.c：SVA 扩展支持。
  • 其他 SoC 驱动
    • apple-dart.c：Apple DART IOMMU。
    • exynos-iommu.c：Samsung Exynos。
    • msm_iommu.c/h、msm_iommu_hw-8xxx.h：Qualcomm MSM。
    • mtk_iommu.c / mtk_iommu_v1.c / mtk_iommu.h：MediaTek。
    • rockchip-iommu.c：Rockchip。
    • sun50i-iommu.c：Allwinner。
    • tegra-gart.c / tegra-smmu.c：NVIDIA Tegra。
    • sprd-iommu.c：Spreadtrum。
    • omap-iommu.c / omap-iommu-debug.c / omap-iommu.h：TI OMAP。
    • s390-iommu.c：IBM s390 架构。
    • virtio-iommu.c：基于 virtio 的虚拟 IOMMU。
    • hyperv-iommu.c：微软 Hyper-V 的 IOMMU 接口。
    • fsl_pamu*.c/h：Freescale PAMU。

5. Glue / 总线绑定

  • of_iommu.c：解析 Device Tree 中的 iommus 属性，建立 device → iommu 绑定。

设备、驱动、总线

虽然 IOMMU 不是这个模型，但是补充一下基础知识。

Linux 下存在一个 设备-驱动-总线 三元组模型。bus 提供规则，负责匹配设备和驱动。device 表示“我有一个硬件”。driver 表示“我能驱动某种硬件”。当 device 和 driver 都在同一个总线类型上存在时，由该总线的 .match() 函数决定是否调用 driver 的 .probe()。

  1. OS 会在子系统初始化（subsys_init）时先初始化总线框架，包括 PCI 总线、USB 总线、Platform 总线，不同总线代表着不同的“匹配规则，每一个设备、驱动都需要挂载到一种总线上，后续基于相同的总线进行匹配和绑定。
  2. 有了总线框架为基础，紧接着就会进行设备发现，总线框架会基于各自的发现规则来发现硬件设备，比如 PCI 总线通过遍历 PCI 配置空间发现新的设备。
  3. 最后执行驱动注册（device_initcall）时，总线框架会基于 id 表、compatible 字符串或 vendor/device id 等进行匹配检查，若该 driver 与之前扫描到的 device 匹配，则调用 driver 的 probe 实现对设备驱动的加载。
  4. 以上为冷插拔匹配模式，但是驱动先加载也是可以的，后续热插拔设备连接时也会触发总线匹配并调用对应驱动 probe。

驱动加载方式

initcall 机制用于静态加载驱动，Linux内核为不同驱动的加载顺序定义了不同的优先级，这些优先级通过一系列的宏来定义，如pure_initcall、core_initcall、postcore_initcall、arch_initcall、subsys_initcall、fs_initcall、rootfs_initcall、device_initcall和late_initcall等。这些宏的优先级依次降低，可以看出其中子系统初始化要早于设备初始化。

注意下图的内核启动顺序中的 driver_init 位于 drivers/base/init.c，只是 buses、devices、classes 等基础框架的初始化（创建 kset，在 sysfs 暴漏节点），并不是具体驱动的初始化（具体驱动初始化位于 do_initcalls）。而内核中的 device_initcall 才是注册一个驱动到总线上，之所以是这个名字，个人认为除了历史原因外，在 Linux 设备模型中广义的 device 的适用范围很广，可以视 device 为一切与设备相关的体系。

其中，内核有两种方式加载驱动。

  1. 静态加载：在静态加载的情况下，所有模块的程序都被编译到Linux内核中，由do_initcall函数负责加载。这些模块按照它们在__initcall_start和__initcall_end之间定义的顺序（即按照优先级和链接顺序）被依次加载。
  2. 动态加载：在系统启动后，可以通过insmod命令手动加载驱动模块，而rmmod命令则用于卸载驱动模块。动态加载的驱动模块不受 initcall 机制的限制，其加载顺序由用户决定。

但是 IOMMU 比较特殊，它不是一个传统设备+驱动+总线的模型，硬件是 CPU 的一部分。IOMMU 不经过总线，总线识别不到 IOMMU，且驱动也不需要注册到总线上。以 Intel 为例，其 IOMMU 初始化过程位于 intel/dmar.c，通过 DMA remapping reporting (DMAR) ACPI 表来发现一个或多个硬件并注册驱动的，相当于绕过了总线，由 IOMMU 驱动直接通过 MMIO 管理硬件。

初始化整体流程

首先简单总结 x86 架构 IOMMU 初始化的整体流程：

  1. 内核启动
  2. 参数解析：iommu_setup
  3. iommu 检测发现：detect_intel_iommu
  4. core initcall：iommu_init
  5. subsys initcall：iommu_subsys_init
  6. rootfs initcall：intel_iommu_init

iommu_setup用于最早期的参数解析，通过 early_param 注册。启动参数的解析是最优先完成的工作，因此 early_param 的调用时机先于以下所有机制，在获取 cmdline 后将使用 do_early_param 依次回调，不展开讲了。

针对 x86 架构，IOMMU 的检测发现有一个独立于 initcall 的初始化路径，即通过写入.iommu_table段的方式实现注册、OS 启动时将在相应时机遍历段和调用相应指针。顺便一提，Linux内核中的各种注册机制都是一样的原理，包括 initcall 和 early_param，其核心原理都是利用链接器的 section 机制，也就是__attribute__((__section__("name")))来实现的，只不过写入的段不同、初始化时机不同。

IOMMU_INIT_POST 这个宏在展开后会成为.iommu_table 段里的静态表项，里面包含 detect_intel_iommu 函数指针。这些表项在启动时会被位于 arch/x86/kernel/pci-dma.c中的 pci_iommu_alloc 调用。detect_intel_iommu 中包含了对x86_init.iommu.iommu_init结构体的赋值，这样后续在 rootfs 级别的 initcall 中调用pci_iommu_init时就可以正常调用目标回调也就是intel_iommu_init了，具体代码后续再分析。

pci_iommu_alloc 在start_kernel → setup_arch中被调用，发生在 PCI 总线初始化之前。

在 detect 完成后，将在 core 和 subsys 两个 initcall 级别完成其他初始化任务，由于比较简单，下文直接展开讲了。

首先是 kset 创建 iommu_groups 暴漏到 sysfs，建立 debugfs。

之后是子系统初始化，首先检查启动命令和内核配置，设置启动模式（passthrough / translated），以及通过内核启动参数来检查 TLB 禁用策略（strict / lazy）。

passthrough 就是 IOMMU_DOMAIN_IDENTITY，translated 就是 IOMMU_DOMAIN_DMA，其他模式如下所示。

  • IOMMU_DOMAIN_BLOCKED - All DMA is blocked, can be used to isolate devices
  • IOMMU_DOMAIN_IDENTITY - DMA addresses are system physical addresses
  • IOMMU_DOMAIN_UNMANAGED - DMA mappings managed by IOMMU-API user, used for VMs
  • IOMMU_DOMAIN_DMA - Internally used for DMA-API implementations. This flag allows IOMMU drivers to implement certain optimizations for these domains
  • IOMMU_DOMAIN_DMA_FQ - As above, but definitely using batched TLB invalidation.

硬件检测

detect_intel_iommu在启动阶段探测并验证 ACPI DMAR 表，确认平台是否支持 Intel IOMMU（VT-d），并注册intel_iommu_init到x86_init.iommu.iommu_init，后续会在 rootfs initcall 级别被调用。
